# 00. Methodology

## Data
`data/customers.csv`: 50,000 simulated customers, 14 fields (see `09_data_model_and_dictionary.md`). Generated by `data/generate_dataset.py`; churn depends on rules built into the generator (for example more tickets and more inactivity raise churn probability). The analysis therefore demonstrates a method; it does not prove real-world effects.

## Definitions
Churn rate, High Risk, extra churn and all other metrics are defined in `03_metric_dictionary.md`.

## Method
1. Data quality checks: 50,000 rows, no missing values, no duplicate IDs.
2. Baseline churn and segment cuts (contract, tier, region, tenure, tickets, inactivity) in SQL (`sql/`) and Power BI.
3. Driver sizing: extra churn per driver against the rest-of-base rate (an upper bound; drivers overlap).
4. Combination analysis: churn by warning-sign combination (3+ tickets, 30+ days inactive).
5. Dashboard (three pages) built from the same definitions; checked with 13 UAT cases (`08_uat_test_cases.md`).

## Validation on real data (IBM Telco, 7,043 customers)
| Pattern | Simulated | IBM Telco | Held? |
|---|---|---|---|
| Month-to-Month churns more | 17.3% vs 8.9% | 42.7% vs 6.8% | Yes (stronger) |
| New customers churn more | 22% (0-6m) vs 10.5% (36m+) | 52.9% vs 11.9% | Yes (stronger) |
| Support tickets, inactivity days | see FINDINGS.md | No such columns | Cannot be validated |

## Limitations
- Synthetic data: findings recover rules built into the generator.
- `risk_score` in the CSV is the generated churn probability (max 58) and is not used.
- No customer's spend falls more than 10% over 3 months, so the spend-drop hypothesis cannot be tested.
- Single snapshot: tenure and signup cohort cannot be separated.
- No cost or outcome data: no ROI is claimed. Impact must be measured with a holdout test.
